# 上架材料（Zotero 中文社区插件商店）

> **状态：材料已备好，但提交被一个前置条件挡住 —— 需要一个 GitHub 仓库。**
>
> 这不是选择，是采集器的硬性要求（见下）。等你建好仓库，把本文里的
> `<OWNER>` / `<REPO>` 两处替换掉，就能直接提 Issue 或 PR。

---

## 为什么必须先有一个 GitHub 仓库

商店的数据由采集器（`zotero-chinese/zotero-plugins` 的 `src/handler/`）生成，
它通过 **GitHub REST API（Octokit）**取插件的身份信息：

```ts
const [owner, repo] = base.repo.split("/");
await octokit.rest.repos.get({ owner, repo }); // 仓库名、描述、stars、作者
```

因此：

| 事项                           | 是否必须来自 GitHub                                                      |
| ------------------------------ | ------------------------------------------------------------------------ |
| 清单里的 `repo` 字段           | **是** —— 类型注释写明是 `owner/name`，且有正则 `^[\w-]+\/[\w.-]+$` 校验 |
| 插件名称 / 描述 / stars / 作者 | **是** —— 全部来自 `repos.get` / `users.getByUsername`                   |
| XPI 的下载地址                 | **否** —— `customLink` 支持非 GitHub 来源                                |

**`customLink` 是本项目能继续从 Gitee 分发 xpi 的通道**，商店里已经
有 4 个插件这么做（`l0o0/MagicZotero`、`MuiseDestiny/zotero-gpt` 等），
网站代码还专门注明：

> 注意：`github` 键的值不一定是 GitHub 链接（如部分插件为 Gitee 直链），
> 因此必须原样保留，不能按固定格式推导。

所以**最少需要**：一个 GitHub 仓库（**可以没有任何 release**，只要仓库存在）、
并在 `src/plugins.ts` 里用 `tagName: "custom"` 指回 Gitee。

## 一、清单条目（PR 时加到 `src/plugins.ts`）

按仓库名排序插入。把 `<OWNER>` / `<REPO>` 换成实际的 GitHub 仓库：

```ts
{
  repo: '<OWNER>/<REPO>',
  releases: [
    {
      // ⚠️ 只支持 Zotero 10 —— 见 addon/manifest.json 的 strict_min/max_version
      targetZoteroVersion: '10',
      tagName: 'custom',
      customLink:
        'https://gitee.com/laofashi666/dsh-for-zotero/releases/download/v0.3.0/dsh-for-zotero.xpi',
    },
  ],
  tags: ['ai', 'reader', 'notes'],
  discoverReleases: true,
},
```

### 字段说明（都是实际值，不是示意）

| 字段                  | 我们的值                  | 依据                                                                                                           |
| --------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `repo`                | `<OWNER>/<REPO>`          | **必须是 GitHub**                                                                                              |
| `targetZoteroVersion` | `'10'`                    | 产物 manifest：`strict_min_version: "10.0"`、`"10.*"`                                                          |
| `tagName`             | `'custom'`                | xpi 由 Gitee 直链分发                                                                                          |
| `customLink`          | Gitee Release 附件        | **已实测 200、可匿名下载**                                                                                     |
| `tags`                | `['ai','reader','notes']` | 商店实际使用的标签只有 8 个：`ai` `reader` `interface` `metadata` `attachment` `integration` `notes` `utility` |
| `discoverReleases`    | `true`                    | 让采集器也能从 GitHub 仓库发现新版本（若那边也发 release，可改用普通 `tagName` + `assetName`，更稳）           |

### ⚠️ `customLink` 用哪个地址（**需要你定**）

| 方案                 | 地址                                            | 取舍                                                                                            |
| -------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **A. Release 附件**  | `…/releases/download/v0.3.0/dsh-for-zotero.xpi` | 已验证可匿名下载。但**版本号写死在地址里**，每次发版都要改清单条目                              |
| **B. 仓库 raw 路径** | `…/raw/main/dist/dsh-for-zotero.xpi`            | 地址**固定不变**，发版只需覆盖那个文件；但需要把 xpi 提交进仓库（约 200 KB/次，会撑大仓库历史） |

现有 4 个用 `customLink` 的插件**全都用 raw 路径**（`…/raw/master/xxx.xpi`）——
因为那样地址稳定。**建议 B**，代价是仓库里多一份二进制；若你不想让仓库变大，就用 A。

还有一个**必须你自己决定的点**：Gitee 的 raw 路径是 `…/raw/<分支>/<路径>`，
要放 xpi 就得让它在仓库里。这与 `.gitignore` 排除构建产物的做法冲突 ——
所以**现在先不改**，等你选定后我再一次性做好。

## 二、投稿正文（Issue 或 PR 描述）

可直接用：

> **插件**：DSH-for-Zotero
> **仓库**：https://gitee.com/laofashi666/dsh-for-zotero（镜像：`https://github.com/<OWNER>/<REPO>`）
**用途**：把 DeepSeek Harness 的 Agent 接进 Zotero，让它**直接读写文献库** ——
读论文全文、按主题整理标签、跨文献对比、把结论写成笔记。会话以真实的 Zotero
附件形态挂在库里（网页链接），双击即在 Zotero 内打开。
**下载**：见 `customLink`
> **Zotero 版本**：仅支持 **10.x**
> **许可证**：MIT
>
> **⚠️ 使用前提**：需要一个本机的 DeepSeek Harness 桌面端 —— 插件会从它提取一份
> **隔离运行时**（独立端口/凭据，与用户桌面版互不干扰），首次约 330 MB、10–30 秒。
> 这一点请在收录时保留说明，否则用户装了会发现"什么也没发生"。
>
> **安全边界**：读与写（改标签/加笔记/加入分类）直接执行并进 Zotero 撤销栈；
> **新建条目与删除必须先由用户在会话页确认**，不会自动执行。

**需要一并告知审核者的两点**（避免被当成缺陷）：

1. **必须装 DSH 桌面端**，不是纯插件 —— 没有它插件无法工作。
2. 首次启动会有一段准备时间（提取运行时），期间界面只有进度窗口。

## 三、提交前自检（采集器的硬性要求）

| 要求                                                                             | 我们的状态                       |
| -------------------------------------------------------------------------------- | -------------------------------- |
| XPI 里有 `manifest.json`                                                         | ✅                               |
| manifest 含 `id`                                                                 | ✅ `dsh-for-zotero@zotero.cn`    |
| manifest 含顶层 `version`                                                        | ✅ `0.3.0`                       |
| manifest 含 `applications.zotero` 的 `strict_min_version` / `strict_max_version` | ✅ `10.0` / `10.*`               |
| `repo` 不与现有条目重复（大小写不敏感）                                          | 待定（取决于仓库名）             |
| `releases.length > 0` 或 `discoverReleases: true`                                | ✅ 两者都有                      |
| `update_url` / 图标 / 许可证                                                     | 采集器**不检查**（我们本来就有） |

> 采集器对 manifest 不完整会直接拒收，报错原文是
> `XPI manifest lacks ID, version or Zotero compatibility range`。
> 我们这几项都齐，不会卡在这里。

## 四、提交入口

- **PR**：fork `zotero-chinese/zotero-plugins` → 在 `src/plugins.ts` 里按仓库名排序加条目 → 提 PR。
  PR 只触发 `pnpm lint:fix` 的检查，全量采集在合并后跑。
- **Issue**：https://github.com/zotero-chinese/zotero-plugins/issues/new
  （模板要求填 **GitHub 仓库 URL**，并勾选"已搜索过现有插件"）
- 商店首页的「🏪 请求收录插件」按钮就指向这个仓库。
